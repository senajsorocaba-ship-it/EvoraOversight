# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is not an application codebase — it's the SQL schema + RLS (Row Level Security) design for **Évora Oversight**, a multi-tenant Supabase/PostgreSQL backend serving political/legislative "gabinete" (office) clients. There is no build tooling, package manager, or test runner here; the "code" is raw SQL meant to be pasted into the Supabase SQL Editor and run in a fixed order.

## Execution order (do not reorder)

1. Run the schema file first (`AO SUPABASE BLOCO1.md.txt` content) — creates types, the 24 tables, constraints, indexes, `atualizado_em` triggers, and the immutable-audit trigger.
2. Then run the RLS file (`evora rls mvp v1.sql` / `BLOCO_2_RLS.md`) — creates the JWT-claim helper functions and the RLS policies (17 base + FARUS/Aegis sections 16-17 from Fases 10-11 — the `BLOCO_2_RLS.md` acceptance count predates those and hasn't been re-verified against the live count; treat "17" there as stale until someone re-runs `select count(*) from pg_policies where schemaname='public'`).
3. Then run the acceptance test (`evora rls teste aceite v1.sql` / `BLOCO_3_TESTE_ACEITE.md`) to prove the RLS layer actually behaves as designed, not just that it compiled.
4. Then run the briefing engine (`evora briefing motor mvp v1.sql`) to get the two aggregator functions in place.
5. BLOCO 5 (`evora auth mvp v1.sql` / `BLOCO_5_AUTENTICACAO.md`) only needs steps 1-2 done first — it's independent of 3 and 4, and can run any time after the RLS layer exists. It also requires a manual dashboard step (enabling the Custom Access Token hook) that no SQL script can perform.

Without step 2, the database has **no isolation between tenants** — this is explicitly called out in the schema file's closing comment. Never treat BLOCO 2 or BLOCO 3 as optional.

After running BLOCO 2, the expected manual acceptance check is:
```sql
select count(*) as politicas from pg_policies where schemaname='public';
```
This must return **17** (13 in the original MVP → 15 after Fase 6 → 17 after Fase 7's `municipios_leitura_publica`/`municipio_fontes_leitura_publica`).

BLOCO 3 automates the four acceptance scenarios plus one bonus check, ending in a `NOTICE: TESTE DE ACEITE: PASSOU — 4 de 4 cenários oficiais OK (+ bônus: ...)`. If a scenario fails, the script raises `CENARIO N FALHOU: ...` and the transaction is left open/aborted — run a bare `rollback;` before retrying. The whole script always ends in `ROLLBACK`, so its fixtures (two fictitious tenants, fontes, one auditoria row) never persist even on success.

## Execution layer (`evora_motor_execucao.py`)

- This is the "motor do briefing" / trusted server-side job that BLOCO 2's `service_role` comment and BLOCO 4 both refer to. It is meant to run from a server, a cron job, or a scheduled cloud function — **never** from a browser, mobile app, or anything a tenant user can reach, because it holds the `service_role` key.
- It calls Claude via the official `anthropic` Python SDK (per this project's `claude-api` conventions), not raw HTTP — that's a deliberate deviation from the zero-dependency style of the sibling `D:\motor\*.py` scripts, which predate the current SDK guidance.
- Persona and formatting rules are adapted from `D:\motor\montador_briefing_evora.py`, generalized to read the authority's name/cargo/partido/temas from `tenants` instead of being hardcoded to one tenant. Markdown→HTML rendering is adapted from `D:\motor\render_briefing_evora.py`.
- Required env vars: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY` (optional: `ANTHROPIC_MODEL_BRIEFING`, default `claude-opus-5`). None of these are ever printed, logged, or written to disk by the script.
- It does not touch `briefings.ciencia_por`/`ciencia_em`/`entregue_em` — giving ciência and delivering a briefing are still manual, application-side actions by a user with `alcada_aprovacao`. Don't add auto-ciência to this script without an explicit owner decision; it would break the freio humano principle. Even if it tried, `evora_valida_ciencia_briefing()` (BLOCO 2) would reject it: `ciencia_por` must match the currently authenticated JWT subject, and `service_role` requests carry no such claim.
- **`--todos` mode** processes every `tenants.ativo = true` row instead of one explicit `--tenant-id` — the orchestration body was extracted into `processar_tenant()` (called identically by both modes, zero behavior change for the pre-existing single-tenant path) so a loop in `main()` can call it per tenant. A tenant's failure (including non-`SystemExit` errors like `anthropic.AuthenticationError` — confirmed by real testing that catching only `SystemExit` let one bad tenant abort the whole run) is caught and reported without stopping the remaining tenants; the process exits non-zero only after every tenant was attempted, if at least one failed.
- **Scheduler**: `.github/workflows/briefing-diario.yml` runs `evora_coletor_mencoes.py --todos` then `evora_motor_execucao.py --todos --mundo gabinete` daily via GitHub Actions (no server/VPS exists for this project, so Actions was chosen over provisioning new infra), plus `workflow_dispatch` for manual runs. Only `gabinete` is scheduled — no tenant has `campanha` data yet, so scheduling it would just spend API cost on empty blocks; `campanha` remains available manually via `--mundo campanha`. Requires 3 repo secrets (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY`) — a manual step outside any script. Deliberately filters by `tenants.ativo` only, not `operacional`/`ciencia_travas` — those two flags aren't checked anywhere else in the system, and every Fase 8 self-registered tenant is born with `operacional = false` with no UI to change it, so filtering on it would silently exclude every self-registered vereador from ever getting a briefing.

## Coletor de menções por nome (`evora_coletor_mencoes.py`)

- Bloco 6 (Imprensa) originally only surfaced city-wide coverage (the `fontes` declared list, populated manually). This script adds the other half: **what's being said about the vereador specifically**, searched by name via Google News RSS (`news.google.com/rss/search` — a public, unauthenticated, undocumented endpoint; same class of risk already accepted for the Fase 9 vigia's Câmara-site fetch). Writes into the same `mencoes_imprensa` table Fase 6 already reads for this block — no schema change needed, `consulta` (added in Fase 6, "qual busca do coletor encontrou este item") already existed for exactly this purpose.
- An equivalent collector (`imprensa_coletor_evora.py`) exists in the sibling `D:\motor` project but isn't reachable from this repo/environment — this is an independent recreation, not a port, so its exact search strategy may differ from the original.
- **Base queries, derived only from existing `tenants` columns** (no new cadastro field for "apelido"): `"<nome_autoridade>"` (exact phrase) and `"<primeiro nome>" "<municipio_sede>"`. The first name ALONE was deliberately rejected — real testing against the "Tatiane Costa" fixture (Sorocaba/PL) confirmed it returns real coverage of the actual person (TRE, candidacy registration) mixed with at least one confirmed false positive (a different "Dra. Tatiane Costa" candidate in Rio Grande do Norte) — combining first name with city cuts that noise without requiring a new field; the exact-full-name query alone can still surface a same-named different person, which is why this is documented as a list of candidate mentions for human reading, not a verified fact.
- **Plus one `site:<dominio>` query per already-known local outlet** (`buscar_dominios_locais`) — reuses whatever's already declared, never discovers a new outlet on its own: the tenant's own `fontes` (`esfera in ('municipal','regional')` only — a national outlet like G1 doesn't help disambiguate a same-named person elsewhere in Brazil) plus, if the tenant's `municipio_sede`/`uf` text matches a row in `municipios`, that city's `municipio_fontes` (Atlas Municipal, Fase 7 — platform-shared, so it can help even a tenant with zero `fontes` of its own, if the Atlas already covers that city). No FK from `tenants` to `municipios` exists, so the match is by name/uf text (`ilike`) — a known limitation, not a bug. Confirmed by real testing: for a city with real local outlets declared, these `site:`-scoped queries returned only genuine coverage of the actual local person, zero false positives — a much stronger signal than the base queries alone. A tenant/city with nothing declared in either table just gets the two base queries, same as before this addition — graceful degradation, not a hard requirement.
- Same `--tenant-id`/`--todos` CLI shape and per-tenant failure isolation as `evora_motor_execucao.py` (see above) — including catching `Exception`, not just `SystemExit`, from the start. A 1-second pause between tenants in `--todos` is a courtesy to Google's endpoint, not a requirement Google imposes.
- No `ANTHROPIC_API_KEY` needed — this script only fetches and parses structured RSS, it never drafts text.

### Non-negotiable principles baked into the schema (do not weaken without an explicit owner decision)

1. **Multi-tenant by row** — every content table carries `tenant_id` referencing `tenants(id)`. All access must be scoped by it. **Exception**: `tenants` itself (it *is* the tenant) and the five platform-shared tables (`municipios`/`municipio_fontes`/`municipio_trilha` from Fase 7, `municipio_vereadores`/`municipio_vereadores_pendencias` from Fases 8-9) — platform-shared data about a city is deliberately readable by every tenant of that city (or, for `municipio_vereadores`, checked against by an unauthenticated visitor during signup), not isolated. See the dedicated Atlas, Autocadastro, and Vigia subsections below. **A third variant, from Fase 10**: `farus_itens` is shared by territory when `origem_aquisicao` is `coleta_programada`/`descoberta_radar` (no owner at all — not even the platform, just no `tenant_id`), but becomes tenant-owned (`tenant_origem` required) when it's `interesse_tenant`/`demanda_tenant` — one table, two access rules depending on a column, enforced by both a CHECK constraint and the RLS policy. See "FARUS" below.
2. **Separation of "mundos" (worlds)** — content tables carry a `mundo` column (`gabinete` | `campanha`, enum `evora_mundo`). This is "Princípio Inviolável nº 4": office business and campaign business must never cross. `lugares` and `desdobramento_eventos` are the exceptions (no `mundo` column — see inline comments explaining why). The only sanctioned crossing point is the "Ponte Bia↔Nil", which happens at the application layer and must be logged to `auditoria` — see `evora_registrar_travessia` (BLOCO 2, section 18 below) for the function that does this.
3. **Two separation levels** — `tenants.nivel_separacao` is `logico` (shared schema, MVP default) or `fisico` (premium, dedicated separation). One schema serves both; this is pending legal/architecture sign-off ("parecer P25").
4. **LGPD-readiness in `demandas`** — citizen-request rows carry consent (`consentimento`, `consentimento_data`), legal basis (`base_legal`), sensitive-data flag (`dado_sensivel`), and retention date (`retencao_ate`). A check constraint (`demandas_dado_pessoal_exige_consentimento`) blocks storing an identified citizen name without recorded consent. **Do not use real citizen data before the P8/P9 legal review lands — use fictitious data for testing.**
5. **Nothing is deleted** — soft delete via `ativo`/`ativa` boolean columns everywhere instead of `DELETE`. `auditoria` is the one exception in the other direction: it is insert-only and immutable (enforced by both a trigger and RLS — see below), never soft-deleted or edited.
6. **Provenance fields travel with external data** — anything sourced externally (`fontes`, etc.) carries fields like `fonte`, `url`, `selo` (CVI seal), `consultado_em`. Don't drop provenance columns when touching these tables.

### RLS design (BLOCO 2)

- Supabase issues a JWT per authenticated request; the app is responsible for writing `tenant_id` and `mundo` into the JWT's `app_metadata`.
- `evora_claims()` reads `request.jwt.claims` defensively — missing, empty, or malformed settings all resolve to `NULL`.
- `evora_tenant_atual()` / `evora_mundo_atual()` extract `tenant_id`/`mundo` from claims (checking `app_metadata` first, falling back to top-level claim).
- `evora_ve_os_dois_mundos()` returns true only for active users with `papel in ('autoridade', 'auditor')` and `mundo_permitido is null` — these are the only roles legitimately allowed to see both worlds.
- **Fail closed is the deliberate default**: a missing/invalid JWT means these functions return `NULL`, and every policy comparison against `NULL` denies access rather than allowing it. Preserve this property in any policy changes.
- RLS is both `enable`d and `force`d on every table (defense in depth — forcing means even the table owner role is subject to RLS).
- Content tables use a `for all using (tenant_id = evora_tenant_atual() and (mundo = evora_mundo_atual() or evora_ve_os_dois_mundos()))` pattern with matching `with check`. `usuarios`, `lugares`, and `desdobramento_eventos` isolate by `tenant_id` only (no `mundo` column). `tenants` only allows `select` of one's own row and blocks client-side `update` entirely (tenant admin is a `service_role`-only operation). `auditoria` allows `select` only to the two-world roles and allows `insert` only — there is intentionally no `update`/`delete` policy, so RLS denies those outright in addition to the immutability trigger.
- The `service_role` key bypasses RLS entirely by Supabase design. It is meant only for trusted server-side jobs (e.g., the briefing engine) and must never be exposed to a browser, mobile app, or committed to the repo.
- **Freio humano (v10.8)**: `briefings.ciencia_por`/`ciencia_em` (renamed from `aprovado_por`/`aprovado_em` — the v10.6 name implied approval-before-reading, which the v10.8 Manual corrected: reading needs no prior approval, ciência is required only before any act with external effect). The `briefings_isolamento` RLS policy alone would let any tenant+mundo user set `ciencia_por` to anyone's id; `evora_valida_ciencia_briefing()` (a `before update` trigger, not a policy — RLS `with check` can't compare against arbitrary other tables' columns the way a trigger can) closes that gap: `ciencia_por` must equal a `usuarios.id` in the same tenant with `alcada_aprovacao` and `ativo`, whose `auth_user_id` matches the *currently authenticated* JWT `sub` — so a user can only give ciência as themselves, never on someone else's behalf, and `ciencia_em` is always server-stamped (`now()`), never client-supplied. `service_role` requests carry no `sub` claim, so this also blocks the motor de execução from ever setting it, even by accident.
- **Travessia de mundo / Ponte Bia↔Nil (section 18)**: `evora_registrar_travessia(p_mundo evora_mundo)` is the one sanctioned way to cross the gabinete/campanha boundary referenced by principle #2 above. It does NOT touch the token — RLS still checks `mundo` straight from the JWT on every table — it only (a) refuses the call unless `evora_ve_os_dois_mundos()` is true for the caller (only `autoridade`/`auditor` with `mundo_permitido is null`), and (b) inserts one `auditoria` row (`acao = 'travessia_ponte'`) before returning `p_mundo` back to the caller, which the application then uses to decide which mundo to request data for in that session. Plain `language plpgsql`, no `security definer` — unlike the BLOCO 5 auth-bootstrap functions, everything it does (`select` on `usuarios`, `insert` on `auditoria`) the calling `authenticated` role can already do directly via its own grants/policies; the function only adds the validation and bundles it into one call. Ported into this repo from a standalone SQL package uploaded for reference (`sql/`, since discarded — it also carried the base 11-table schema/RLS/auth predating Fases 6-9 and the v10.8 `ciencia_por` rename, and would have been a regression if used as-is); this was the one genuinely new piece in it. Not yet called from anywhere in `web/` — the Bia↔Nil bridge UI itself doesn't exist yet, so this function has no caller today, only the RLS/audit half of the mechanism.
- **Trava do módulo Demandas (section 19, Manual v11.0)**: the "Caderno do Programador" (companion to the Manual Supremo v11.0, 16/09/2026) states the Demandas module stays off until a legal opinion (parecer jurídico) lands — it handles citizen personal data (name, contact, geolocation) without that sign-off yet. `tenants.demandas_parecer_juridico` (BLOCO 1, default `false` for every tenant) holds the decision; `evora_travar_demandas_sem_parecer()` (a `before insert or update` trigger, not just an RLS `with check`, so the error message can be explicit rather than a generic "row-level security policy violated") is what actually enforces it — raises unless the row's `tenant_id` has that flag `true`. Blocks writes only, not `select` — fixture/test data already in the table (the seed's two Sorocaba demandas) stays readable, including by `/api/bia`. `supabase/seed.sql`'s tenant insert sets the flag `true` explicitly for the fictitious pilot tenant only (with a comment explaining why) — every other/future/real tenant is born locked. As of this writing, `web/`'s own `/demandas` page never talked to Supabase anyway (static mockup numbers, confirmed by grep for `createClient`/`supabase.` — zero hits) — so this trigger is what actually turns the module off at the one place that mattered: the database.

### Atlas Municipal (Fase 7, Anexo 16)

- **`municipios`/`municipio_fontes`/`municipio_trilha` are platform-shared, NOT tenant-scoped** — no `tenant_id`, no `mundo`, same category of exception as `tenants` itself. Two tenants in the same city read the same `municipios` row; that's the point (media outlets, Diário Oficial platform, and other city-level facts shouldn't be re-verified per tenant).
- RLS pattern is inverted from every other table: `for select using (true)` — open read to any `authenticated` role, gated only by the `grant select` (no `insert`/`update`/`delete` policy or grant for `authenticated` at all — anti-poisoning is enforced at the grant level, before RLS even runs). Only `service_role` writes, always via `evora_atlas_municipal.py`, never a user-facing form.
- `municipio_fontes` mirrors `fontes`' F1/F2/F3 columns but fixes a real bug: `fontes`' own `fontes_f3_nunca_compartilhada` CHECK is tautological (`mundo` is `not null default 'gabinete'`, so the condition can never be false) — `municipio_fontes_nunca_f3` here is unconditional (`check (nivel <> 'F3')`) since this table can only ever be the shared layer, F3 (personal influencers) can never legitimately appear in it.
- `mapa_politico_factual` (on `municipios`) and `diario_oficial.conector_com` exist in *shape* only — no TSE collector or Diário Oficial connector exists anywhere in this repo, so don't populate them with fabricated/stubbed data. This is the same "don't add a table or fabricate data until a real collector exists" rule from the Briefing engine section above, generalized from tables to columns.
- Operated via `evora_atlas_municipal.py` (`semear`/`validar`/`aplicar`/`importar`), same `service_role`/PostgREST/stdlib-only pattern as `evora_ingestao_coletores.py`. No self-serve onboarding UI exists ("Entrevista de Fundação", Anexo 16 §5) and none was built in Fase 7 — it would require designing a platform-admin role from scratch (`evora_papel` is entirely tenant-scoped; there is no platform-wide role anywhere in this schema, RLS, or the `web/` frontend). Treat that as a separate, later owner decision, not an implicit side effect of touching this schema.

### Autocadastro de vereador (Fase 8)

- **`municipio_vereadores` holds the one piece of data the Atlas never had**: a real, human-verified roster of a municipality's sitting vereadores with their institutional email — the gate for self-registration ("only someone whose email is on this city's list can register as vereador"). Investigated at length before building this: no such roster exists anywhere — not in `municipios.legislativo` (aggregate fields only: `num_vereadores`, `composicao_partidaria`, etc.), not in the original file-based prototype, not in the Manual's Anexo 16 (which restricts political data to aggregate TSE facts, "Leitura A" — never personal email). No TSE or per-Câmara collector exists to generate it automatically (every Câmara Municipal has its own website), so — same rule as everywhere else in this file — it is **never fabricated**: it's seeded manually via `evora_atlas_municipal.py vereadores adicionar`, one real, sourced record at a time, same operating model as `municipio_fontes`.
- **A city with zero rows in `municipio_vereadores` simply has self-registration closed** — `evora_verificar_vereador` returns no match for any email, so nobody can complete signup for that city until an owner seeds it with real data. Sorocaba was seeded right after shipping (25 real vereadores, sourced from `camarasorocaba.sp.gov.br/page.html?tag=faleconosco`) — every other city starts with zero rows and stays closed until seeded the same way.
- **Bulk seeding**: `vereadores importar-lote <slug> <arquivo.csv-ou-json> --fonte "..."` reads a whole city's roster at once (CSV columns `nome,email[,partido]`, or a JSON list of the same) instead of one `adicionar` call per person. It **upserts** by e-mail (`_upsert_vereador`: insert, or update-in-place on a unique-constraint conflict) — re-running it with a refreshed export from the same Câmara page is exactly how the roster is meant to be kept current across elections/turnover, not just how it's seeded the first time.
- RLS: `enable`+`force`, but **unlike `municipios`/`municipio_fontes`, there is no `grant select` to `authenticated` at all** — same as `municipio_trilha`. A vereador's institutional email is sensitive enough that it's never exposed via a direct REST query, not even to other authenticated tenants. The only access path is the two read functions below, which answer one email at a time and can never be used to enumerate the roster.
- **Three `security definer` functions** in `evora_auth_mvp_v1.sql` (BLOCO 5), same family as `evora_token_hook`/`evora_vincular_auth_user` — they must work for a caller with no identity yet (an anonymous visitor picking state/city), so `execute` is granted to `anon`:
  - `evora_listar_municipios_uf(p_uf)` — lists Atlas-seeded cities for a state (only cities the Atlas already knows about show up as signup options).
  - `evora_verificar_vereador(p_municipio_id, p_email)` — checks one email against `municipio_vereadores`, returns eligibility + name if matched.
  - `evora_autocadastro_vereador(p_municipio_id, p_email)` — re-validates eligibility and email uniqueness internally (never trusts the prior check alone — TOCTOU), then inserts `tenants`+`usuarios` (papel `autoridade`) and returns the new `tenant_id`. The caller (the `/cadastro` page in `web/`) must call `supabase.auth.signUp()` with the same email right after — the existing BLOCO 5 trigger links `usuarios.auth_user_id` automatically, same as any manually-provisioned tenant.
- **Why RPCs and not a new Next.js API route with a `service_role` client**: `web/` has neither today. Adding one would introduce the `service_role` secret into the Next.js server runtime for the first time. These RPCs do the same job with the already-public `anon` key, exactly the same trust model BLOCO 5's hook already uses ("has to work before the caller has identity" → `security definer`, not elevated client credentials). Smaller new surface, same audited pattern.
- No approval queue after signup — the owner's explicit choice was that a matched email creates an active account immediately; the email-on-the-roster check *is* the human-verification gate (the roster itself was human-verified at seed time).

### Cloud default-privilege bug found and fixed (2026-08-23)

Real end-to-end testing of the cadastro flow against the **cloud** project (not local) surfaced that the cloud project had an inherited `ALTER DEFAULT PRIVILEGES` (legacy Supabase behavior — the current default, used locally per `config.toml`, does not do this) silently granting **every** privilege — select/insert/update/delete on every table, execute on every function — to `anon` and `authenticated` on every object created by `postgres` in `public`, since Fase 1. No migration in this repo ever asked for this. RLS was catching everything on the table side (verified live: `INSERT`/`DELETE` via the `anon` key against `municipio_vereadores` were rejected/no-op), but `evora_gerar_briefing_diario`/`evora_montar_blocos_briefing` (BLOCO 4, `security definer`, bypass RLS *by design*, meant for `service_role` only) were genuinely callable by an unauthenticated `anon` caller with **any** `tenant_id` — a real cross-tenant data exposure, not just a theoretical defense-in-depth gap.

Fixed in `supabase/migrations/20260823000001_fix_grants_padrao.sql`: `revoke all ... from anon, authenticated` on every table and function in `public`, then re-grant exactly the documented set (mirroring BLOCO 2's table grants and the Fase 8 function grants), plus `alter default privileges for role postgres in schema public revoke all on tables/functions from anon, authenticated` so future migrations don't silently regain this. Re-verified after the fix: BLOCO 3's automated RLS test still passes 4/4+bonus, a full signup→login→see-own-tenant cycle still works, `municipio_vereadores` now returns an explicit 401 instead of a silent empty array, and `evora_gerar_briefing_diario` now correctly rejects an unauthenticated caller.

**Lesson for future migrations on this project**: never assume "I didn't grant X to anon/authenticated" means X is actually inaccessible to them — check `information_schema.role_table_grants`/`role_routine_grants` against the live project (cloud and local can differ) rather than trusting the absence of an explicit grant statement in the migration you just wrote.

### Vigia de vereadores (Fase 9)

- **Solves a narrower problem than "know every vereador in Brazil"** — there is no such source (TSE has no email; each of Brazil's ~5,570 Câmaras has its own unstructured website). The vigia only re-checks cities that already have `municipios.vereadores_fonte_url` configured — a real column (not jsonb) because `vigiar-todas` needs to query "every city with a URL set" structurally. Onboarding a new city's URL is still a one-time manual step (`vereadores configurar-fonte-url`), same kind of work as seeding the roster itself.
- **`vereadores vigiar <slug>`** downloads the configured URL (stdlib `urllib`; needs a browser-like `User-Agent` — confirmed against Sorocaba's real site, which 403s any script-looking UA via a generic WAF despite having no `robots.txt` disallowing anything; it's a public institutional contact page, so this is treated the same as opening it manually, not evading auth). Extraction is **regex/heuristic first, no IA, no dependency at all** (`_extrair_vereadores_heuristica`): most Câmara sites publish this as a plain `<tr><td>nome</td><td>email</td></tr>` table (often literally pasted from Word/Excel), so it finds every table row containing an e-mail-shaped string, pairs it with the row's other cell if that cell looks like a person's name (Title Case, 2-6 words, allowing lowercase connectors like "de"/"da"), and dedupes by e-mail. Verified 25/25 correct, zero false positives, against Sorocaba's real page. **Only falls back to the Claude API** (official SDK, same call shape as `evora_motor_execucao.py`'s `client.messages.create(..., output_config={"effort": ...})`) if the heuristic returns 0 or an unreasonable count AND `ANTHROPIC_API_KEY` is set — explicitly instructed to never invent an email not literally present, mirroring the briefing motor's "never invent what step 1 didn't provide." Uses a cheap/fast model (`ANTHROPIC_MODEL_VIGIA`, default `claude-haiku-4-5-20251001`) and low effort when it does run. A sanity check aborts (no pendências written) if extraction — either method — returns 0 people or more than 60 (Brazil's largest câmara, São Paulo, has 55) — a strong signal it grabbed page noise instead of a real roster. Without a heuristic match and without an API key, `vigiar` fails with a clear message instead of silently doing nothing.
- **Never writes to `municipio_vereadores` directly.** The diff (by email, falling back to name-match for detecting an email change) only inserts rows into `municipio_vereadores_pendencias` (`tipo`: `novo`/`email_alterado`/`possivel_saida`), deduped against already-`pendente` rows from a prior run. This is deliberate: an unreviewed AI extraction writing straight into the table that gates who can self-register as a vereador would be the anti-poisoning trave being defeated by the exact mechanism meant to keep it fresh.
- **`vereadores pendencias listar/aplicar/rejeitar <slug>`** is the human review step — `aplicar` calls the same `_upsert_vereador` Fase 8 already tests (or flips `ativo=false` for `possivel_saida`), stamps `revisado_por`/`revisado_em`, and logs to `municipio_trilha`; `rejeitar` just marks the pendência discarded. Nothing here bypasses the `selo='verificado'` requires-`fonte` rule.
- **No scheduler runs `vigiar`/`vigiar-todas` automatically.** The briefing motor gained one (`.github/workflows/briefing-diario.yml`, see the Execution layer section above) after this was written, but `vigiar-todas` was deliberately not added to it — unlike the briefing/mentions collector, applying its output is never automatic (`municipio_vereadores_pendencias` always needs human review), so scheduling the *detection* step alone without the review step being solved too would just pile up an ever-growing queue nobody looks at. `vigiar-todas` remains a manual command until that's an explicit owner decision.

### FARUS — Acervo Territorial de Informação Verificada (Fase 10, Manual v10.9.1)

- **Successor of "Veritas-Dados"**, the shared verified-data repository the Manual referenced (under that name) since v7.7 without it ever being built. Delivered as a self-contained pair of files (`evora farus f1.sql` + `evora farus teste aceite.sql`, already 10/10) written against an assumed 11-table base; adapted here into BLOCO 1 (types + tables 19-22 + `farus_hash` + the retention trigger) and BLOCO 2 (RLS section 16 + `farus_territorios_do_tenant()`) of the tables/RLS this repo actually has — content is otherwise unchanged from what was delivered. The as-delivered originals are archived at `_versoes_anteriores/farus_aegis_entregues_v10_9_1/`.
- **A third, different exception to "multi-tenant by row"** (see principle #1 above): the acervo is shared by **município** (`farus_territorios`/`farus_tenant_territorios` — same "collect once, serve every tenant of that city" economics as the Atlas Municipal), but unlike the Atlas, a `farus_itens` row can ALSO belong to one tenant's private research. The fork is the `origem_aquisicao` column: `coleta_programada`/`descoberta_radar` → shared, `tenant_origem` must be `null`; `interesse_tenant`/`demanda_tenant` → private, `tenant_origem` is required. Enforced twice — a CHECK constraint (`farus_item_origem_coerente`) and the RLS policy (`farus_itens_leitura`, "territory the tenant follows AND (public OR mine)") — so a code bug in one layer doesn't leak a tenant's private search to their city's other clients. Verified live by the delivered acceptance test: two gabinetes in Sorocaba share the public decree, gabinete B never sees gabinete A's private research, and a third gabinete in Campinas sees neither.
- **Fonte lifecycle mirrors the Atlas's anti-poisoning discipline**: `descoberta → observada → configurada`, and a CHECK constraint (`farus_fonte_liberacao_humana`) blocks the `configurada` state without `liberada_por`/`liberada_em` set — decision D6 (Anexo 16) applied to FARUS too, so a fonte the autonomous radar (F3, not built yet) discovers can never silently start feeding a briefing.
- **Deduplication is one function, `farus_hash`** — SQL `IMMUTABLE`, normalizes case/whitespace/accents via `translate` (a fixed lookup table), never `unaccent` (that function is `STABLE`, since its dictionary can change; marking an `IMMUTABLE` wrapper around a `STABLE` call is accepted by Postgres and silently corrupts any index built on it — this is a real bug the delivered file's own changelog reports finding and fixing before handoff). Any future collector writing to `farus_itens` must call this same function for its `hash_conteudo`, never recompute hashing separately, or the dedup unique index (`ix_farus_itens_dedup`) stops working correctly.
- **Retention is enforced by a `BEFORE DELETE` trigger** (`farus_impedir_exclusao_acervo`), not by convention: any row with `retencao_indeterminada = true` and a shared `origem_aquisicao` raises on delete. Matches this project's existing "nothing is deleted" principle (#5 above), just enforced at the trigger level instead of only via an `ativo` flag, because this table has no soft-delete column at all — deletion is meant to be structurally hard, not merely discouraged.
- **Partial overlap resolved in a later session — the acervo is now actually populated and consumed.** `achados_fiscalizacao`/`mencoes_imprensa` still exist and still feed the briefing (nothing broke), but `farus_itens` is no longer empty or unread:
  - **`evora_coletor_farus.py` (new)** ingests real content into `farus_itens` — general search scoped to the TENANT'S TERRITORY (município as a whole — `"Prefeitura de <cidade>"`, `"Câmara Municipal de <cidade>"`, licitações, decretos, via the same free Google News RSS endpoint `evora_coletor_mencoes.py` already uses), not a specific person's name (that's still `evora_coletor_mencoes.py`'s job). It auto-provisions `farus_territorios`/`farus_tenant_territorios` on first run for a given município — no manual seeding step.
  - **Deliberate decision: no `farus_fontes` catalog is required to ingest.** The fonte lifecycle (`descoberta → observada → configurada`, liberação humana) governs the `farus_fontes` table specifically — a *recurring, catalogued* source. An individual `farus_itens` row does not depend on having a `farus_fontes` row at all (`fonte_id` is nullable) and only requires verification (`verificado_por`/`verificado_em`) when `estado in ('confirmado','corroborado')` — the `farus_item_verificacao_registrada` check imposes nothing on the default `estado = 'nao_verificado'`. This is a straight reading of FARUS's own "Regra pétrea" ("quando não souber, declara que não foi possível verificar"), not a deviation: `evora_coletor_farus.py` never writes `confirmado`/`corroborado`, every item it writes starts and stays `nao_verificado` unless a person promotes it later through the (still unbuilt) F2 catalog UI.
  - **Dedup hash is always computed by the database, never re-implemented in Python** — the collector calls `rpc/farus_hash` per item and uses the returned value directly in the `on_conflict=territorio_id,hash_conteudo` upsert, so it's byte-identical to what any other writer would produce. One real bug found and fixed during testing: Google News occasionally returns the same headline under two different links (e.g. an AMP mirror) — a single batched `INSERT ... ON CONFLICT` cannot resolve the *same* conflict key twice in one statement (`ON CONFLICT DO UPDATE command cannot affect row a second time`); fixed by deduplicating by hash client-side before the insert, not just by link.
  - **`evora_montar_blocos_briefing`** (`evora briefing motor mvp v1.sql`, BLOCO 4) — bloco 6 (Imprensa) now unions a third source (`farus_itens`, filtered by the tenant's territories, respecting the same public/private `tenant_origem` boundary the RLS policy already enforces) alongside `fontes` and `mencoes_imprensa`. Every item in the union now also carries an `estado` field; the aviso text and the system prompt both instruct the drafting model to never present a `nao_verificado` FARUS item as a confirmed fact. Verified live: the Bia's drafted text correctly hedged FARUS items as unverified, and even cross-referenced a FARUS headline against the (empty) Fiscalização block on its own, explicitly declining to treat it as a confirmed finding.
  - **`web/src/app/api/bia/route.ts`** (voice/chat Q&A) also now queries `farus_itens` directly with the user's own session — RLS (`farus_itens_leitura`) already scopes it to the tenant's territories with no extra filtering needed in the route. Same "never present nao_verificado as fact" instruction in its system prompt.
  - **Still not built**: `evora_ingestao_coletores.py` (PNCP/achados_fiscalizacao) does not write to FARUS, and the F2 catalog (human curation UI to promote a `farus_fontes` row to `configurada`, or an item to `confirmado`) doesn't exist — both remain deliberately out of scope, not blockers for F1 ("Apenas a F1 condiciona o lançamento" — Manual, Faseamento aprovado).
- **`tenants.plano`** (`municipal`/`estadual`/`nacional`, Manual E12) was added now, defaulted to `municipal` for every existing row, specifically so a future billing/entitlement change doesn't need its own migration later — the column costs nothing today and is expensive to retrofit once populated.

### Aegis A0 — Cofre de Dado Sensível (Fase 11, Manual v10.9.1)

- **The vault for sensitive personal data (N5)** — CPF and birth date today (`aegis_especie` also reserves `documento_identidade`/`dado_saude`/`dado_seguranca` for later, not collected). Delivered as `evora aegis a0.sql` + `evora aegis teste aceite.sql` (10/10), adapted into BLOCO 1 (tables 23-24 + the immutability trigger) and BLOCO 2 (RLS section 17 + `aegis_ler`/`aegis_mascara`). As-delivered originals archived alongside FARUS's at `_versoes_anteriores/farus_aegis_entregues_v10_9_1/`.
- **The rule the whole module exists to guarantee, verbatim from the Manual**: *if the vault has to open for routine operation, it isn't a vault.* Nothing in login, the briefing, or any screen may depend on the vaulted content — only on `aegis_mascara()`, which never opens `aegis_cofre` and never writes to the access log.
- **The only real adaptation made**: the delivered file used Supabase's `auth.uid()` to identify the calling user inside `aegis_ler`; this project has never used that helper anywhere else — it uses its own, already-audited `evora_claims() ->> 'sub'` (same idiom as `evora_valida_ciencia_briefing`, RLS section 15). The access check itself is unchanged (`papel in ('autoridade','chefe_gabinete')` — confirmed `chefe_gabinete` already exists in this project's own `evora_papel` enum, so no enum change was needed).
- **`aegis_cofre` has no SELECT policy at all for `authenticated`** — not a restrictive one, *none* — same "absence is the protection" pattern already used for `municipio_vereadores`. The only read path is `aegis_ler(usuario_id, especie, motivo, justificativa)`, which looks up the caller's role, raises if they're not `autoridade`/`chefe_gabinete`, inserts into `aegis_acessos` **before** returning the value (a read with no log entry cannot happen — verified by test: reading then counting the access row always finds exactly one), and only then returns the plaintext. `aegis_acessos` is itself append-only via the same immutable-trigger pattern as `auditoria`.
- **Masks are stored, not computed** — `aegis_cofre.mascara` lives next to `valor` but is a separate column, checked by two CHECK constraints (`aegis_mascara_parcial`: mask can never equal the real value; `aegis_mascara_oculta`: mask must contain `•` or `*`) so a bug can't accidentally store an unmasked value as if it were the mask.
- **A0 is intentionally the smallest possible version**: no envelope encryption (planned as A1), no quorum/fragmentation (A2, ties to the still-unbuilt Sigma One). Today's protection is entirely RLS/grant-level (no SELECT policy + provider-level encryption at rest) — sufficient because, per the Manual's own verification before building this, no sensitive field was ever actually being written anywhere in this system yet. That window (vault built before the first sensitive value exists) is why A0 was cheap; it will never be this cheap again.

### Reconhecimento facial no modo descanso — deliberate deviation from the Manual (web/, not this schema)

- **Lives entirely in `web/`** (`web/src/lib/reconhecimento-facial.ts`, `web/src/lib/trava-tela.ts`, `web/src/components/enrolamento-facial.tsx`, `web/src/components/vigia-presenca.tsx`, `web/src/app/modo-descanso/page.tsx`) — noted here anyway because it's a real, deliberate exception to how this project has followed the Manual everywhere else, and needs to be as visible as the FARUS/Aegis adaptations above.
- **The Manual explicitly recommends against this.** `Evora Manual v10 9 1.md` (around lines 1300-1309 and 3666) calls Évora building its own facial recognition "não recomendado" — biometric data is N5 and requires a DPIA (impact assessment, pending under "J9") that was never done — and lists biometria among what "não se liga agora." The Manual's own recommended pattern for "unlock by face" is a **passkey** (the OS's own Face ID/Windows Hello/Touch ID; the biometric data never leaves the device and Évora never becomes its custodian).
- **The user was shown this explicitly, before any code was written, and chose to proceed anyway** — asked directly whether to use passkey (the Manual's recommendation), Évora's own webcam recognition, or presence-only locking with no facial matching at all; picked Évora's own webcam recognition, informed. This section exists so that choice — and its containment — stays visible, not because it was hidden.
- **Containment: the descriptor never leaves the browser.** No new table, no new migration, no new API route — `aegis_cofre`/`aegis_ler` (Fase 11 above) were evaluated and rejected for this specifically because they're structurally the wrong shape for it (only `autoridade`/`chefe_gabinete` can read *any* vault entry, never the owner reading their own; every read is audit-logged, unworkable for a compare-every-few-seconds loop; `unique(usuario_id, especie)` allows only one stored value). Instead, the face descriptor (128 floats derived from the enrollment photos, never the photos themselves) is computed and matched entirely client-side (`@vladmandic/face-api`, TensorFlow.js in the browser) and stored only in that browser's `localStorage`, keyed per user id. Évora's server never receives, stores, or transmits it.
- **This reduces but does not eliminate the real exposure.** It is still Évora's own code processing biometric data — a proper DPIA is still the correct next step before this is exposed to real users beyond this development environment, not just this local containment.
- **Known limitations, documented in the UI copy itself, not hidden**: no liveness/anti-spoof comparable to a real depth-sensing Face ID — only a lightweight heuristic (two matching detections a fraction of a second apart, with a small landmark-position shift between them, meant to rule out a static printed photo, nothing more); works only on the device/browser where the face was enrolled (clearing browser storage erases it, a different browser needs re-enrollment); a "usar senha" escape hatch always exists on the lock screen so nobody can be trapped by a failed match.
- **Presence-based auto-lock, not just idle-timeout**: per the user's explicit choice, the webcam runs continuously (one frame every ~3s) while the dashboard is open — not only at the lock screen — so it locks within seconds of the person leaving the frame, not only after the pre-existing 2-minute mouse/keyboard idle timer. It only ever activates for a user who has enrolled a face; nobody's camera turns on without that explicit opt-in from Configurações.
- **A pre-existing, unrelated bug was fixed as part of this work**: the inactivity lock (`InactivityGuard` in `web/src/components/dashboard-shell.tsx`) was purely client-side React state — reloading the page while "locked" bypassed it entirely. Closed with a `sessionStorage` flag (`web/src/lib/trava-tela.ts`) checked on every dashboard mount, cleared only by a successful face match, the "usar senha" fallback, or logout.

## Working conventions for this schema

- SQL, comments, and documentation are written in Brazilian Portuguese; keep new additions consistent with that (mirror existing terminology like `mundo`, `tenant`, `fonte`, `desdobramento` rather than translating).
- Every new content table should follow the existing shape: `tenant_id uuid not null references tenants(id)`, a `mundo` column if it is world-scoped content, an `ativo`/`ativa` soft-delete boolean, and a matching RLS policy added to BLOCO 2 in the same style as the others.
- When adding a table, update the schema file, the RLS file, and the acceptance-test expected policy count in `BLOCO_2_RLS.md` (last updated at 17, before Fases 8-11 — treat it as stale, re-run `select count(*) from pg_policies where schemaname='public'` against a fresh `db reset` rather than trusting the written number). If the new table is tenant+mundo scoped, add matching fixtures/assertions to BLOCO 3 (`evora rls teste aceite v1.sql` / `BLOCO_3_TESTE_ACEITE.md`) so the isolation and mundo-separation scenarios cover it too. (The Atlas Municipal tables, Fase 7, `municipio_vereadores`, Fase 8, `municipio_vereadores_pendencias`, Fase 9, and FARUS/Aegis, Fases 10-11, are the deliberate exception — they're platform-shared or hybrid, not plain tenant-scoped, so BLOCO 3's tenant-isolation fixtures don't apply to them; each has its own dedicated acceptance test instead — see the dedicated subsections above.)
- `auditoria` must remain insert-only from every angle (trigger + RLS). Do not add an `update`/`delete` policy to it under any circumstance short of an explicit owner decision.
