# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is not an application codebase — it's the SQL schema + RLS (Row Level Security) design for **Évora Oversight**, a multi-tenant Supabase/PostgreSQL backend serving political/legislative "gabinete" (office) clients. There is no build tooling, package manager, or test runner here; the "code" is raw SQL meant to be pasted into the Supabase SQL Editor and run in a fixed order.

Files:

Creates fictitious fixtures, switches to the `authenticated` role, simulates different JWT claims, and asserts (via `RAISE EXCEPTION`) the isolation/separation/immutability/fail-closed guarantees — then rolls back so nothing persists.

## Execution order (do not reorder)

1. Run the schema file first (`AO SUPABASE BLOCO1.md.txt` content) — creates types, the 17 tables, constraints, indexes, `atualizado_em` triggers, and the immutable-audit trigger.
2. Then run the RLS file (`evora rls mvp v1.sql` / `BLOCO_2_RLS.md`) — creates the JWT-claim helper functions and the 17 RLS policies.
3. Then run the acceptance test (`evora rls teste aceite v1.sql` / `BLOCO_3_TESTE_ACEITE.md`) to prove the RLS layer actually behaves as designed, not just that it compiled.
4. Then run the briefing engine (`evora briefing motor mvp v1.sql`) to get the two aggregator functions in place.
5. BLOCO 5 (`evora auth mvp v1.sql` / `BLOCO_5_AUTENTICACAO.md`) only needs steps 1-2 done first — it's independent of 3 and 4, and can run any time after the RLS layer exists. It also requires a manual dashboard step (enabling the Custom Access Token hook) that no SQL script can perform.

Without step 2, the database has **no isolation between tenants** — this is explicitly called out in the schema file's closing comment. Never treat BLOCO 2 or BLOCO 3 as optional.

After running BLOCO 2, the expected manual acceptance check is:
```sql
select count(*) as politicas from pg_policies where schemaname='public';
```
This must return **17** (13 in the original MVP → 15 after Fase 6 → 17 after Fase 7's `municipios_leitura_publica`/`municipio_fontes_leitura_publica`).

BLOCO 3 automates the four acceptance scenarios plus one bonus check, ending in a `NOTICE: TESTE DE ACEITE: PASSOU — 4 de 4 cenários oficiais OK (+ bônus: ...)`. If a scenario fails, the script raises `CENARIO N FALHOU: ...` and the transaction is left open/aborted — run a bare `rollback;` before retrying. The whole script always ends in `ROLLBACK`, so its fixtures (two fictitious tenants, fontes, one auditoria row) never persist even on success.

## Execution layer (`evora_motor_execucao.py`)

- This is the "motor do briefing" / trusted server-side job that BLOCO 2's `service_role` comment and BLOCO 4 both refer to. It is meant to run from a server, a cron job, or a scheduled cloud function — **never** from a browser, mobile app, or anything a tenant user can reach, because it holds the `service_role` key.
- It calls Claude via the official `anthropic` Python SDK (per this project's `claude-api` conventions), not raw HTTP — that's a deliberate deviation from the zero-dependency style of the sibling `D:\motor\*.py` scripts, which predate the current SDK guidance.
- Persona and formatting rules are adapted from `D:\motor\montador_briefing_evora.py`, generalized to read the authority's name/cargo/partido/temas from `tenants` instead of being hardcoded to one tenant. Markdown→HTML rendering is adapted from `D:\motor\render_briefing_evora.py`.
- Required env vars: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ANTHROPIC_API_KEY` (optional: `ANTHROPIC_MODEL_BRIEFING`, default `claude-opus-5`). None of these are ever printed, logged, or written to disk by the script.
- It does not touch `briefings.ciencia_por`/`ciencia_em`/`entregue_em` — giving ciência and delivering a briefing are still manual, application-side actions by a user with `alcada_aprovacao`. Don't add auto-ciência to this script without an explicit owner decision; it would break the freio humano principle. Even if it tried, `evora_valida_ciencia_briefing()` (BLOCO 2) would reject it: `ciencia_por` must match the currently authenticated JWT subject, and `service_role` requests carry no such claim.

## Domain architecture

### The 18 core tables
`tenants`, `usuarios`, `fontes`, `briefings`, `demandas`, `lugares`, `compromissos`, `atas`, `desdobramentos`, `desdobramento_eventos`, `auditoria` — the original 11 (ratified in "Anexo 14 da v10.6"). Plus `achados_fiscalizacao` and `mencoes_imprensa`, added in Fase 6 of the test plan (an explicit owner decision, per this file's own rule below) to give the PNCP and press collectors (`D:\motor\coletor_pncp_evora.py`, `imprensa_coletor_evora.py`) a real ingestion target instead of JSON-only output. Plus `municipios`, `municipio_fontes`, `municipio_trilha`, added in Fase 7 (also an explicit owner decision) for the Atlas Municipal (Anexo 16) — see the dedicated subsection below, since these three deliberately break rule #1 just below. Plus `municipio_vereadores`, added in Fase 8 (also an explicit owner decision) to back self-registration for the "vereador" role — see the "Autocadastro de vereador" subsection below, since it's in the same rule-#1-breaking family as the Atlas tables. Plus `municipio_vereadores_pendencias`, added in Fase 9, holding the vigia's proposed diffs pending human review — see "Vigia de vereadores" below. Don't add/remove tables without an explicit decision from the project owner.

### Non-negotiable principles baked into the schema (do not weaken without an explicit owner decision)

1. **Multi-tenant by row** — every content table carries `tenant_id` referencing `tenants(id)`. All access must be scoped by it. **Exception**: `tenants` itself (it *is* the tenant) and the five platform-shared tables (`municipios`/`municipio_fontes`/`municipio_trilha` from Fase 7, `municipio_vereadores`/`municipio_vereadores_pendencias` from Fases 8-9) — platform-shared data about a city is deliberately readable by every tenant of that city (or, for `municipio_vereadores`, checked against by an unauthenticated visitor during signup), not isolated. See the dedicated Atlas, Autocadastro, and Vigia subsections below.
2. **Separation of "mundos" (worlds)** — content tables carry a `mundo` column (`gabinete` | `campanha`, enum `evora_mundo`). This is "Princípio Inviolável nº 4": office business and campaign business must never cross. `lugares` and `desdobramento_eventos` are the exceptions (no `mundo` column — see inline comments explaining why). The only sanctioned crossing point is the "Ponte Bia↔Nil", which happens at the application layer and must be logged to `auditoria`.
3. **Two separation levels** — `tenants.nivel_separacao` is `logico` (shared schema, MVP default) or `fisico` (premium, dedicated separation). One schema serves both; this is pending legal/architecture sign-off ("parecer P25").
4. **LGPD-readiness in `demandas`** — citizen-request rows carry consent (`consentimento`, `consentimento_data`), legal basis (`base_legal`), sensitive-data flag (`dado_sensivel`), and retention date (`retencao_ate`). A check constraint (`demandas_dado_pessoal_exige_consentimento`) blocks storing an identified citizen name without recorded consent. **Do not use real citizen data before the P8/P9 legal review lands — use fictitious data for testing.**
5. **Nothing is deleted** — soft delete via `ativo`/`ativa` boolean columns everywhere instead of `DELETE`. `auditoria` is the one exception in the other direction: it is insert-only and immutable (enforced by both a trigger and RLS — see below), never soft-deleted or edited.
6. **Provenance fields travel with external data** — anything sourced externally (`fontes`, etc.) carries fields like `fonte`, `url`, `selo` (CVI seal), `consultado_em`. Don't drop provenance columns when touching these tables.

### RLS design (BLOCO 2)

- Supabase issues a JWT per authenticated request; the app is responsible for writing `tenant_id` and `mundo` into the JWT's `app_metadata`.
- `evora_claims()` reads `request.jwt.claims` defensively — missing, empty, or malformed settings all resolve to `NULL`.
- `evora_tenant_atual()` / `evora_mundo_atual()` extract `tenant_id`/`mundo` from claims (checking `app_metadata` first, falling back to top-level claim).
- `evora_ve_os_dois_mundos()` returns true only for active users with `papel in ('autoridade', 'auditor')` and `mundo_permitido is null` — these are the only roles legitimately allowed to see both worlds.
- **Fail closed is the deliberate default**: a missing/invalid JWT means these functions return `NULL`, and every policy comparison against `NULL` denies access rather than allowing it. Preserve this property in any policy changes.
- RLS is both `enable`d and `force`d on every table (defense in depth — forcing means even the table owner role is subject to RLS).
- Content tables use a `for all using (tenant_id = evora_tenant_atual() and (mundo = evora_mundo_atual() or evora_ve_os_dois_mundos()))` pattern with matching `with check`. `usuarios`, `lugares`, and `desdobramento_eventos` isolate by `tenant_id` only (no `mundo` column). `tenants` only allows `select` of one's own row and blocks client-side `update` entirely (tenant admin is a `service_role`-only operation). `auditoria` allows `select` only to the two-world roles and allows `insert` only — there is intentionally no `update`/`delete` policy, so RLS denies those outright in addition to the immutability trigger.
- The `service_role` key bypasses RLS entirely by Supabase design. It is meant only for trusted server-side jobs (e.g., the briefing engine) and must never be exposed to a browser, mobile app, or committed to the repo.
- **Freio humano (v10.8)**: `briefings.ciencia_por`/`ciencia_em` (renamed from `aprovado_por`/`aprovado_em` — the v10.6 name implied approval-before-reading, which the v10.8 Manual corrected: reading needs no prior approval, ciência is required only before any act with external effect). The `briefings_isolamento` RLS policy alone would let any tenant+mundo user set `ciencia_por` to anyone's id; `evora_valida_ciencia_briefing()` (a `before update` trigger, not a policy — RLS `with check` can't compare against arbitrary other tables' columns the way a trigger can) closes that gap: `ciencia_por` must equal a `usuarios.id` in the same tenant with `alcada_aprovacao` and `ativo`, whose `auth_user_id` matches the *currently authenticated* JWT `sub` — so a user can only give ciência as themselves, never on someone else's behalf, and `ciencia_em` is always server-stamped (`now()`), never client-supplied. `service_role` requests carry no `sub` claim, so this also blocks the motor de execução from ever setting it, even by accident.

### Atlas Municipal (Fase 7, Anexo 16)

- **`municipios`/`municipio_fontes`/`municipio_trilha` are platform-shared, NOT tenant-scoped** — no `tenant_id`, no `mundo`, same category of exception as `tenants` itself. Two tenants in the same city read the same `municipios` row; that's the point (media outlets, Diário Oficial platform, and other city-level facts shouldn't be re-verified per tenant).
- RLS pattern is inverted from every other table: `for select using (true)` — open read to any `authenticated` role, gated only by the `grant select` (no `insert`/`update`/`delete` policy or grant for `authenticated` at all — anti-poisoning is enforced at the grant level, before RLS even runs). Only `service_role` writes, always via `evora_atlas_municipal.py`, never a user-facing form.
- `municipio_fontes` mirrors `fontes`' F1/F2/F3 columns but fixes a real bug: `fontes`' own `fontes_f3_nunca_compartilhada` CHECK is tautological (`mundo` is `not null default 'gabinete'`, so the condition can never be false) — `municipio_fontes_nunca_f3` here is unconditional (`check (nivel <> 'F3')`) since this table can only ever be the shared layer, F3 (personal influencers) can never legitimately appear in it.
- `mapa_politico_factual` (on `municipios`) and `diario_oficial.conector_com` exist in *shape* only — no TSE collector or Diário Oficial connector exists anywhere in this repo, so don't populate them with fabricated/stubbed data. This is the same "don't add a table or fabricate data until a real collector exists" rule from the Briefing engine section above, generalized from tables to columns.
- Operated via `evora_atlas_municipal.py` (`semear`/`validar`/`aplicar`/`importar`), same `service_role`/PostgREST/stdlib-only pattern as `evora_ingestao_coletores.py`. No self-serve onboarding UI exists ("Entrevista de Fundação", Anexo 16 §5) and none was built in Fase 7 — it would require designing a platform-admin role from scratch (`evora_papel` is entirely tenant-scoped; there is no platform-wide role anywhere in this schema, RLS, or the `web/` frontend). Treat that as a separate, later owner decision, not an implicit side effect of touching this schema.

### Autocadastro de vereador (Fase 8)

- **`municipio_vereadores` holds the one piece of data the Atlas never had**: a real, human-verified roster of a municipality's sitting vereadores with their institutional email — the gate for self-registration ("only someone whose email is on this city's list can register as vereador"). Investigated at length before building this: no such roster exists anywhere — not in `municipios.legislativo` (aggregate fields only: `num_vereadores`, `composicao_partidaria`, etc.), not in the original file-based prototype, not in the Manual's Anexo 16 (which restricts political data to aggregate TSE facts, "Leitura A" — never personal email). No TSE or per-Câmara collector exists to generate it automatically (every Câmara Municipal has its own website), so — same rule as everywhere else in this file — it is **never fabricated**: it's seeded manually via `evora_atlas_municipal.py vereadores adicionar`, one real, sourced record at a time, same operating model as `municipio_fontes`.
- **A city with zero rows in `municipio_vereadores` simply has self-registration closed** — `evora_verificar_vereador` returns no match for any email, so nobody can complete signup for that city until an owner seeds it with real data. Sorocaba was seeded right after shipping (25 real vereadores, sourced from `camarasorocaba.sp.gov.br/page.html?tag=faleconosco`) — every other city starts with zero rows and stays closed until seeded the same way.
- **Bulk seeding**: `vereadores importar-lote <slug> <arquivo.csv-ou-json> --fonte "..."` reads a whole city's roster at once (CSV columns `nome,email[,partido]`, or a JSON list of the same) instead of one `adicionar` call per person. It **upserts** by e-mail (`_upsert_vereador`: insert, or update-in-place on a unique-constraint conflict) — re-running it with a refreshed export from the same Câmara page is exactly how the roster is meant to be kept current across elections/turnover, not just how it's seeded the first time.
- RLS: `enable`+`force`, but **unlike `municipios`/`municipio_fontes`, there is no `grant select` to `authenticated` at all** — same as `municipio_trilha`. A vereador's institutional email is sensitive enough that it's never exposed via a direct REST query, not even to other authenticated tenants. The only access path is the two read functions below, which answer one email at a time and can never be used to enumerate the roster.
- **Three `security definer` functions** in `evora_auth_mvp_v1.sql` (BLOCO 5), same family as `custom_access_token_hook`/`evora_vincular_auth_user` — they must work for a caller with no identity yet (an anonymous visitor picking state/city), so `execute` is granted to `anon`:
  - `evora_listar_municipios_uf(p_uf)` — lists Atlas-seeded cities for a state (only cities the Atlas already knows about show up as signup options).
  - `evora_verificar_vereador(p_municipio_id, p_email)` — checks one email against `municipio_vereadores`, returns eligibility + name if matched.
  - `evora_autocadastro_vereador(p_municipio_id, p_email)` — re-validates eligibility and email uniqueness internally (never trusts the prior check alone — TOCTOU), then inserts `tenants`+`usuarios` (papel `autoridade`) and returns the new `tenant_id`. The caller (the `/cadastro` page in `web/`) must call `supabase.auth.signUp()` with the same email right after — the existing BLOCO 5 trigger links `usuarios.auth_user_id` automatically, same as any manually-provisioned tenant.
- **Why RPCs and not a new Next.js API route with a `service_role` client**: `web/` has neither today. Adding one would introduce the `service_role` secret into the Next.js server runtime for the first time. These RPCs do the same job with the already-public `anon` key, exactly the same trust model BLOCO 5's hook already uses ("has to work before the caller has identity" → `security definer`, not elevated client credentials). Smaller new surface, same audited pattern.
- No approval queue after signup — the owner's explicit choice was that a matched email creates an active account immediately; the email-on-the-roster check *is* the human-verification gate (the roster itself was human-verified at seed time).

### Cloud default-privilege bug found and fixed (2026-08-23)

Real end-to-end testing of the cadastro flow against the **cloud** project (not local) surfaced that the cloud project had an inherited `ALTER DEFAULT PRIVILEGES` (legacy Supabase behavior — the current default, used locally per `config.toml`, does not do this) silently granting **every** privilege — select/insert/update/delete on every table, execute on every function — to `anon` and `authenticated` on every object created by `postgres` in `public`, since Fase 1. No migration in this repo ever asked for this. RLS was catching everything on the table side (verified live: `INSERT`/`DELETE` via the `anon` key against `municipio_vereadores` were rejected/no-op), but `evora_gerar_briefing_diario`/`evora_montar_blocos_briefing` (BLOCO 4, `security definer`, bypass RLS *by design*, meant for `service_role` only) were genuinely callable by an unauthenticated `anon` caller with **any** `tenant_id` — a real cross-tenant data exposure, not just a theoretical defense-in-depth gap.

Fixed in `supabase/migrations/20260823000001_fix_grants_padrao.sql`: `revoke all ... from anon, authenticated` on every table and function in `public`, then re-grant exactly the documented set (mirroring BLOCO 2's table grants and the Fase 8 function grants), plus `alter default privileges for role postgres in schema public revoke all on tables/functions from anon, authenticated` so future migrations don't silently regain this. Re-verified after the fix: BLOCO 3's automated RLS test still passes 4/4+bonus, a full signup→login→see-own-tenant cycle still works, `municipio_vereadores` now returns an explicit 401 instead of a silent empty array, and `evora_gerar_briefing_diario` now correctly rejects an unauthenticated caller.

**Lesson for future migrations on this project**: never assume "I didn't grant X to anon/authenticated" means X is actually inaccessible to them — check `information_schema.role_table_grants`/`role_routine_grants` against the live project (cloud and local can differ) rather than trusting the absence of an explicit grant statement in the migration you just wrote.

### Vigia de vereadores (Fase 9)

- **Solves a narrower problem than "know every vereador in Brazil"** — there is no such source (TSE has no email; each of Brazil's ~5,570 Câmaras has its own unstructured website). The vigia only re-checks cities that already have `municipios.vereadores_fonte_url` configured — a real column (not jsonb) because `vigiar-todas` needs to query "every city with a URL set" structurally. Onboarding a new city's URL is still a one-time manual step (`vereadores configurar-fonte-url`), same kind of work as seeding the roster itself.
- **`vereadores vigiar <slug>`** downloads the configured URL (stdlib `urllib`; needs a browser-like `User-Agent` — confirmed against Sorocaba's real site, which 403s any script-looking UA via a generic WAF despite having no `robots.txt` disallowing anything; it's a public institutional contact page, so this is treated the same as opening it manually, not evading auth). Extraction is **regex/heuristic first, no IA, no dependency at all** (`_extrair_vereadores_heuristica`): most Câmara sites publish this as a plain `<tr><td>nome</td><td>email</td></tr>` table (often literally pasted from Word/Excel), so it finds every table row containing an e-mail-shaped string, pairs it with the row's other cell if that cell looks like a person's name (Title Case, 2-6 words, allowing lowercase connectors like "de"/"da"), and dedupes by e-mail. Verified 25/25 correct, zero false positives, against Sorocaba's real page. **Only falls back to the Claude API** (official SDK, same call shape as `evora_motor_execucao.py`'s `client.messages.create(..., output_config={"effort": ...})`) if the heuristic returns 0 or an unreasonable count AND `ANTHROPIC_API_KEY` is set — explicitly instructed to never invent an email not literally present, mirroring the briefing motor's "never invent what step 1 didn't provide." Uses a cheap/fast model (`ANTHROPIC_MODEL_VIGIA`, default `claude-haiku-4-5-20251001`) and low effort when it does run. A sanity check aborts (no pendências written) if extraction — either method — returns 0 people or more than 60 (Brazil's largest câmara, São Paulo, has 55) — a strong signal it grabbed page noise instead of a real roster. Without a heuristic match and without an API key, `vigiar` fails with a clear message instead of silently doing nothing.
- **Never writes to `municipio_vereadores` directly.** The diff (by email, falling back to name-match for detecting an email change) only inserts rows into `municipio_vereadores_pendencias` (`tipo`: `novo`/`email_alterado`/`possivel_saida`), deduped against already-`pendente` rows from a prior run. This is deliberate: an unreviewed AI extraction writing straight into the table that gates who can self-register as a vereador would be the anti-poisoning trave being defeated by the exact mechanism meant to keep it fresh.
- **`vereadores pendencias listar/aplicar/rejeitar <slug>`** is the human review step — `aplicar` calls the same `_upsert_vereador` Fase 8 already tests (or flips `ativo=false` for `possivel_saida`), stamps `revisado_por`/`revisado_em`, and logs to `municipio_trilha`; `rejeitar` just marks the pendência discarded. Nothing here bypasses the `selo='verificado'` requires-`fonte` rule.
- **No scheduler runs `vigiar`/`vigiar-todas` automatically** — same open gap as the daily briefing motor (`evora_motor_execucao.py`), deliberately not solved here to avoid building scheduler infrastructure twice; `vigiar-todas` is the command a future shared scheduler would target for both.

## Working conventions for this schema

- SQL, comments, and documentation are written in Brazilian Portuguese; keep new additions consistent with that (mirror existing terminology like `mundo`, `tenant`, `fonte`, `desdobramento` rather than translating).
- Every new content table should follow the existing shape: `tenant_id uuid not null references tenants(id)`, a `mundo` column if it is world-scoped content, an `ativo`/`ativa` soft-delete boolean, and a matching RLS policy added to BLOCO 2 in the same style as the others.
- When adding a table, update the schema file, the RLS file, and the acceptance-test expected policy count (currently 17) in `BLOCO_2_RLS.md`. If the new table is tenant+mundo scoped, add matching fixtures/assertions to BLOCO 3 (`evora rls teste aceite v1.sql` / `BLOCO_3_TESTE_ACEITE.md`) so the isolation and mundo-separation scenarios cover it too. (The Atlas Municipal tables, Fase 7, `municipio_vereadores`, Fase 8, and `municipio_vereadores_pendencias`, Fase 9, are the deliberate exception — they're platform-shared, not tenant-scoped, so BLOCO 3's tenant-isolation fixtures don't apply to them; see the dedicated subsections above.)
- `auditoria` must remain insert-only from every angle (trigger + RLS). Do not add an `update`/`delete` policy to it under any circumstance short of an explicit owner decision.
